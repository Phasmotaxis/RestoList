2. Solving Doubt #4: Concurrency, Capacity, Mutations &
Money
Here is the exact relational and transactional architecture to solve all four data-integrity problems in PHP 8.3
+ PDO (MySQL 8 & SQLite) without needing external queues or Redis:

A. Preventing Double-Booking Race Conditions (Two-Layer Defense)
A naive UNIQUE(table_id, reservation_time) fails because a 7:00 PM booking for 90 minutes (19:00–20:30)
collides with a 7:30 PM booking (19:30–21:00) even though the timestamps differ. Solve it at both the
transaction layer and the schema layer:
1.​ Explicit Half-Open Time Intervals ([start_at, end_at)): Every reservation stores start_at and end_at
(calculated as start_at + org.turn_duration_minutes + org.buffer_minutes). Two bookings overlap if
and only if:​
existing.start_at<new.end_at∧existing.end_at>new.start_at

2.​ Pessimistic Row Locking Inside PDO::beginTransaction():
○​ MySQL: SELECT id, capacity, is_active FROM dining_tables WHERE org_id = ? AND id IN (...)
ORDER BY id ASC FOR UPDATE (always sorting by id ASC prevents deadlocks when merging
multiple tables).
○​ SQLite (for your test suite): Start the transaction with BEGIN IMMEDIATE so concurrent
writers serialize cleanly at the database lock level.
○​ Run the overlap check inside the transaction; if any active booking (pending, confirmed, seated)
overlaps, rollBack() immediately and offer the waitlist.
3.​ Schema-Level Time-Bucket Guard (reservation_slots): Discretize reservations into 15-minute
intervals and insert (org_id, table_id, slot_start_utc) into a reservation_slots child table with
UNIQUE(org_id, table_id, slot_start_utc). Even if a future developer forgets FOR UPDATE,
MySQL/SQLite itself rejects an overlapping insert with a 23000 integrity constraint violation.

B. Table Capacity & Multi-Table Merging
Replace a single reservations.table_id foreign key with a junction table reservation_tables (reservation_id,
table_id):
●​ When a party of 6 requests a slot at a restaurant with only 4-top tables, the allocator selects adjacent
tables sharing the same zone_id where is_combinable = 1 and ∑capacity≥party_size, locks all
candidate table rows in id ASC order, and inserts one reservations header plus two reservation_tables
rows atomically.

C. Safe Floor Plan & Menu Mutations (Soft-Archive + Active-Booking Guard)
●​ Never hard-delete tables, zones, or menu items referenced by historical or upcoming records (ON
DELETE RESTRICT on all foreign keys).
●​ Add archived_at DATETIME NULL to dining_tables and menu_items.
●​ Before archiving a table or reducing its capacity, run a guard query checking for future active
reservations (end_at > NOW() AND status IN ('pending', 'confirmed')). If any exist, block the edit and
return the conflicting booking IDs so staff can reassign them first.

D. Financial & ERP Inventory Integrity (Centavos + Append-Only Ledgers)
●​ Integer Centavos (BIGINT): Store all prices, reservation deposits, and purchase order totals as
signed integer centavos (₱250.00 = 25000). Zero floating-point drift across PHP, MySQL, and SQLite.
●​ Append-Only Payment & Stock Ledgers:
○​ Deposits write immutable rows to deposit_ledger (id, org_id, reservation_id, entry_type,
amount_centavos, created_at) with entry_type IN ('hold', 'forfeit', 'refund', 'applied_to_bill')
instead of flipping a mutable is_paid boolean.
○​ When [OPTIONAL] inventory tracking is enabled, menu_item_recipes (menu_item_id,
ingredient_id, qty_per_serving) links menu items to raw stock, and every PO receipt or
completed order writes an immutable delta to stock_movements (id, org_id, ingredient_id,
delta_qty, reason, ref_id) so current stock is always auditable.

- **Half-Open UTC Intervals:** Reservations store `[start_at, end_at)` where `end_at = start_at +
turn_duration_minutes + buffer_minutes`. Two bookings overlap iff `existing.start_at < new.end_at AND
existing.end_at > new.start_at` for active statuses (`pending`, `confirmed`, `seated`).​
